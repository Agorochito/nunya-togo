## Explication pas à pas

Une réservation est maintenant un dictionnaire avec les clés id, equipement, debut, fin et active. L’identifiant est un texte stable qui permet de retrouver cette réservation. L’état active est un booléen. Une réservation annulée reste dans l’historique avec active égal à False, mais elle n’occupe plus le créneau. Les fiches déjà enregistrées sont garanties cohérentes dans les exercices.

La disponibilité commence par la validation de la demande. Une demande de durée nulle, inversée ou hors de la journée est indisponible, même si la liste existante est vide. Ensuite, on parcourt les réservations et l’on cherche un conflit : fiche active, même équipement, et chevauchement temporel. Ces trois conditions doivent être vraies ensemble. Une seule fiche conflictuelle suffit pour retourner False.

Si le parcours se termine sans conflit, retourne True. Ne retourne pas True après la première fiche non gênante : une autre réservation peut encore bloquer la demande. Un test avec une fiche libre d’abord puis une fiche conflictuelle ensuite vérifie précisément cet ordre de décision. Une liste vide valide directement toute demande dont les bornes sont correctes.

D’autres lectures utilisent les mêmes critères : compter les réservations actives d’un équipement ou additionner leurs durées. Le cumul de durées n’est pas une preuve de disponibilité, car il ne décrit pas leurs positions dans la journée. Deux agendas possédant la même durée totale peuvent laisser des créneaux libres différents. Choisis donc un bilan qui répond à la question posée et garde les données initiales intactes pour les contrôles suivants.

Les activités appliquent ces règles dans quatre situations complémentaires. La disponibilité combine les trois critères sans confondre historique et occupation. Les demandes adjacentes, annulées et portant sur une autre ressource restent correctement séparées. Le nombre d’engagements est distinct de la durée occupée. Une annulation garde sa fiche mais disparaît du compte actif, ce qui permet de conserver l’historique. Le bilan mesure le temps réservé, sans prétendre révéler les trous de l’agenda. Deux créneaux de même durée peuvent gêner des demandes différentes selon leur position. Une liste d’identifiants fournit un diagnostic précis tout en respectant les mêmes critères de conflit. Le tri assure un résultat stable sans modifier l’ordre de l’historique.

Les horaires sont des entiers représentant des minutes dans une seule journée fictive ; aucun fuseau ni changement de date n’intervient. Dessine les créneaux sur une ligne pour vérifier les frontières. Ne remplace pas les règles par une impression visuelle : le même équipement et l’état actif comptent aussi. Les fonctions retournent des données en mémoire et conservent leurs arguments. Un refus doit être explicable par le contrat annoncé.

## Exemple guidé 1

```python
reservations = [{"id":"r1", "equipement":"A", "debut":540, "fin":600, "active":False}]
nombre = 0
for reservation in reservations:
    if reservation["active"]:
        nombre = nombre + 1
print(nombre)
```

## Exemple guidé 2

```python
reservations = [{"id":"r1", "equipement":"A", "debut":540, "fin":600, "active":True}]
libre = True
for r in reservations:
    if r["active"] and r["equipement"] == "A" and 590 < r["fin"] and r["debut"] < 650:
        libre = False
print(libre)
```
