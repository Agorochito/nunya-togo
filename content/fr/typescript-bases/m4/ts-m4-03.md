## Explication pas à pas

Ce projet réunit le cours autour d’un problème réel : suivre les commandes d’une boutique en ligne. Une commande est créée, puis payée, puis livrée ; elle peut être annulée tant qu’elle n’est pas livrée. Chaque état apporte ses informations : le moyen de paiement une fois payée, le livreur une fois livrée, le motif en cas d’annulation.

La première étape est le modèle. Une union discriminée sur la propriété etat décrit les quatre états, chacun avec exactement ses informations. Une commande « créée » n’a pas de livreur : il est impossible d’en écrire une. Une commande « livrée » a forcément un paiement et un livreur. On dit qu’on rend les états impossibles impossibles à représenter.

Les changements d’état sont aussi modélisés : un événement payer apporte un moyen de paiement, livrer un livreur, annuler un motif. Une fonction avancer(commande, evenement) calcule le nouvel état. Un switch sur le type d’événement, terminé par la vérification never, garantit que tous les événements sont traités. Les règles qui dépendent des valeurs, comme « on ne livre qu’une commande payée », sont vérifiées à l’exécution et lèvent une erreur explicite : les types et les tests se complètent.

Remarque que avancer ne modifie jamais la commande reçue : elle renvoie un nouvel objet. Cette immuabilité simplifie le raisonnement, permet de garder l’historique et évite qu’une erreur à mi-chemin laisse une commande dans un état incohérent.

Viennent ensuite les outils transversaux. Une fonction générique resumer<T extends { etat: string }> compte les éléments par état ; elle fonctionne pour les commandes, mais aussi pour les inscriptions ou les livraisons. À la frontière, une garde de type vérifie les commandes importées d’un fichier JSON avant de les laisser entrer dans le programme.

Ce découpage, modèle, transitions, outils, frontière, est celui de nombreuses applications professionnelles. Une fois le modèle écrit, l’éditeur guide le reste du travail : il propose les états possibles, refuse les propriétés qui n’existent pas, et signale chaque fonction à compléter quand les règles changent.

Tu sais maintenant écrire du TypeScript qui fait travailler le compilateur pour toi. La suite logique est d’utiliser ces types dans un projet réel : une API Node.js typée, ou une interface React en TypeScript, deux usages très demandés en entreprise.

## Exemple guidé 1

```typescript
type Commande =
  | { etat: "créée"; id: number; total: number }
  | { etat: "payée"; id: number; total: number; paiement: string }
  | { etat: "livrée"; id: number; total: number; paiement: string; livreur: string }
  | { etat: "annulée"; id: number; total: number; motif: string };

type Evenement =
  | { type: "payer"; paiement: string }
  | { type: "livrer"; livreur: string }
  | { type: "annuler"; motif: string };

function avancer(c: Commande, ev: Evenement): Commande {
  switch (ev.type) {
    case "payer":
      if (c.etat !== "créée") throw new Error("paiement impossible");
      return { etat: "payée", id: c.id, total: c.total, paiement: ev.paiement };
    case "livrer":
      if (c.etat !== "payée") throw new Error("livraison impossible");
      return { ...c, etat: "livrée", livreur: ev.livreur };
    case "annuler":
      if (c.etat === "livrée" || c.etat === "annulée") throw new Error("annulation impossible");
      return { etat: "annulée", id: c.id, total: c.total, motif: ev.motif };
    default: {
      const impossible: never = ev;
      return impossible;
    }
  }
}

let c: Commande = { etat: "créée", id: 1, total: 4500 };
c = avancer(c, { type: "payer", paiement: "mobile money" });
c = avancer(c, { type: "livrer", livreur: "Kossi" });
console.log(c.etat, c.etat === "livrée" ? c.livreur : "");
```

Affichage attendu :

    livrée Kossi

Trace :

- La commande passe par les états prévus.
- Chaque transition renvoie un nouvel objet.
- Après le test d’état, livreur est accessible.

## Exemple guidé 2

```typescript
type Commande =
  | { etat: "créée"; id: number; total: number }
  | { etat: "payée"; id: number; total: number; paiement: string }
  | { etat: "livrée"; id: number; total: number; paiement: string; livreur: string }
  | { etat: "annulée"; id: number; total: number; motif: string };

type Evenement =
  | { type: "payer"; paiement: string }
  | { type: "livrer"; livreur: string }
  | { type: "annuler"; motif: string };

function avancer(c: Commande, ev: Evenement): Commande {
  switch (ev.type) {
    case "payer":
      if (c.etat !== "créée") throw new Error("paiement impossible");
      return { etat: "payée", id: c.id, total: c.total, paiement: ev.paiement };
    case "livrer":
      if (c.etat !== "payée") throw new Error("livraison impossible");
      return { ...c, etat: "livrée", livreur: ev.livreur };
    case "annuler":
      if (c.etat === "livrée" || c.etat === "annulée") throw new Error("annulation impossible");
      return { etat: "annulée", id: c.id, total: c.total, motif: ev.motif };
    default: {
      const impossible: never = ev;
      return impossible;
    }
  }
}

function resumer<T extends { etat: string }>(liste: T[]): Record<string, number> {
  const r: Record<string, number> = {};
  for (const c of liste) r[c.etat] = (r[c.etat] ?? 0) + 1;
  return r;
}

const toutes: Commande[] = [
  { etat: "créée", id: 1, total: 1000 },
  { etat: "annulée", id: 2, total: 500, motif: "client absent" },
  { etat: "créée", id: 3, total: 800 },
];
console.log(resumer(toutes));
try {
  avancer(toutes[1], { type: "payer", paiement: "espèces" });
} catch (e) {
  console.log((e as Error).message);
}
```

Affichage attendu :

    { 'créée': 2, 'annulée': 1 }
    paiement impossible

Trace :

- resumer compte les commandes par état.
- Elle fonctionnerait pour tout objet ayant un état.
- Payer une commande annulée est refusé à l’exécution.
