## Explication pas à pas

Toutes les vérifications vues jusqu’ici portent sur le code écrit par les développeurs. Mais un programme reçoit aussi des données qu’il ne contrôle pas : le corps d’une requête, un fichier JSON, la réponse d’une API, le stockage du navigateur. TypeScript ne peut pas connaître leur forme à l’avance. JSON.parse renvoie d’ailleurs le type any, qui désactive toute vérification.

La pire réaction est d’affirmer le type avec as : const p = JSON.parse(texte) as Produit. Cette assertion ne vérifie rien : elle dit seulement à TypeScript de croire le développeur. Si le JSON contient un prix écrit en texte, ou pas de prix du tout, le programme continue avec une donnée fausse, et l’erreur apparaît bien plus loin, là où elle est difficile à comprendre.

La bonne méthode consiste à considérer les données externes comme unknown, puis à les vérifier. Une garde de type est une fonction qui fait cette vérification et l’annonce à TypeScript grâce à un prédicat : function estProduit(x: unknown): x is Produit. Elle renvoie un booléen ; quand elle renvoie true, TypeScript sait que x est un Produit dans la suite du code. À l’intérieur, on teste tout ce que le type exige : que x soit un objet non null, que nom soit un texte, que prix soit un nombre.

Cette vérification doit être honnête : si la garde oublie de tester une propriété, TypeScript la croira quand même. Une garde mensongère est aussi dangereuse qu’un as. On la teste donc soigneusement, avec des données valides et invalides.

Pour une liste, on vérifie d’abord Array.isArray, puis chaque élément. Selon le besoin, on refuse toute la liste au premier élément invalide, ou l’on garde les éléments valides et l’on compte les autres, en signalant le problème.

Dans de grands projets, on utilise souvent des bibliothèques de validation, qui décrivent un schéma une fois et en déduisent à la fois la vérification à l’exécution et le type TypeScript. Le principe reste celui-ci : à la frontière du programme, on vérifie ; à l’intérieur, on fait confiance aux types.

Cette discipline rejoint les leçons de sécurité des cours Node.js et cybersécurité : une donnée venue de l’extérieur n’est jamais fiable tant qu’elle n’a pas été vérifiée, et TypeScript, sans vérification à l’exécution, ne change rien à cette règle.

## Exemple guidé 1

```typescript
interface Produit {
  nom: string;
  prix: number;
}

function estProduit(x: unknown): x is Produit {
  return typeof x === "object" && x !== null
    && typeof (x as Produit).nom === "string"
    && typeof (x as Produit).prix === "number";
}

const donnees: unknown = JSON.parse('[{"nom":"riz","prix":600},{"nom":"sel","prix":"150"}]');
if (Array.isArray(donnees)) {
  const valides = donnees.filter(estProduit);
  console.log(valides.map(p => p.nom), donnees.length - valides.length, "invalide");
}
```

Affichage attendu :

    [ 'riz' ] 1 invalide

Trace :

- Le JSON est traité comme unknown.
- La garde vérifie chaque propriété.
- Le prix écrit en texte rend le second produit invalide.

## Exemple guidé 2

```typescript
interface Produit {
  nom: string;
  prix: number;
}

const menteur = JSON.parse('{"nom":"riz"}') as Produit;
console.log(menteur.prix * 2);
```

Affichage attendu :

    NaN

Trace :

- as affirme le type sans vérifier.
- Le prix manque pourtant.
- Le calcul donne NaN, loin de la vraie cause.
