## Explication pas à pas

En JavaScript, beaucoup d’erreurs ne se voient qu’à l’exécution : additionner un nombre et un texte, appeler une fonction avec un argument oublié, lire une propriété mal orthographiée. Le programme se lance, puis produit un résultat absurde ou plante devant l’utilisateur. Dans un grand projet, ces erreurs coûtent cher.

TypeScript, créé par Microsoft en 2012, ajoute à JavaScript un système de types. On écrit let age: number = 16 pour dire que age contient un nombre. Un outil, le compilateur tsc, lit tout le programme et vérifie que chaque valeur est utilisée conformément à son type. Si l’on écrit plus loin age = "seize", tsc refuse : le type string ne peut pas être affecté au type number. L’erreur est signalée avant l’exécution, avec sa ligne, souvent directement dans l’éditeur pendant qu’on tape.

Le code TypeScript ne s’exécute pas tel quel : tsc le transforme en JavaScript ordinaire en retirant les annotations, puis Node.js ou le navigateur exécute ce JavaScript. Les types n’existent donc qu’au moment de la vérification ; ils ne ralentissent pas le programme et ne protègent pas contre les données reçues à l’exécution, un point important pour le module 4.

On n’a pas besoin d’annoter tout. TypeScript devine le type de la plupart des valeurs : c’est l’inférence. Après let ville = "Lomé", ville est un string ; après const notes = [12, 15], notes est un number[]. On annote surtout les paramètres des fonctions et les données dont le type n’est pas évident.

Le mode strict, activé dans tous les projets modernes et dans cet atelier, rend la vérification plus exigeante : un paramètre sans type est refusé, et une valeur qui peut être null ou undefined doit être vérifiée avant usage. Il trouve davantage d’erreurs, ce qui est le but.

TypeScript est devenu un standard dans les entreprises : la plupart des grands projets web, Angular et une grande partie de l’écosystème React l’utilisent. Comme le langage est un sur-ensemble de JavaScript, tout ce que tu sais déjà reste valable ; tu ajoutes seulement des types.

Dans cet atelier, ton code est compilé avec tsc en mode strict, puis exécuté par Node.js. Une erreur de type empêche l’exécution, comme dans un vrai projet configuré avec l’option noEmitOnError. Lis toujours le message : il indique la ligne et ce qui ne correspond pas. Certaines vérifications contrôlent aussi qu’un appel incorrect est bien refusé : des types trop larges, comme any, les font échouer.

## Exemple guidé 1

```typescript
let age: number = 16;
const ville = "Lomé";
const notes = [12, 15, 9];
age = age + 1;
console.log(age, ville.toUpperCase(), notes.length);
```

Affichage attendu :

    17 LOMÉ 3

Trace :

- age est annoté number.
- ville et notes ont un type deviné par inférence.
- Le programme est vérifié, puis exécuté comme du JavaScript.

## Exemple guidé 2

```typescript
function prixTTC(prixHT: number): number {
  return Math.round(prixHT * 1.18);
}

const total: number = prixTTC(1000) + prixTTC(250);
console.log(total);
```

Affichage attendu :

    1475

Trace :

- Le paramètre et le résultat sont annotés.
- Appeler prixTTC("1000") serait refusé avant l’exécution.
- Le JavaScript produit ne contient plus les types.
