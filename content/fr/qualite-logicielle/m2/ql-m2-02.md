## Explication pas à pas

Un bug sans message d’erreur est plus difficile qu’une trace : le programme tourne, mais donne un résultat faux. La tentation est de modifier une ligne au hasard, puis une autre, en espérant que cela s’arrange. Cette méthode fait perdre des heures et ajoute souvent de nouveaux bugs. Les développeurs expérimentés procèdent comme des enquêteurs.

D’abord, reproduire le problème de façon fiable, avec un exemple précis : telle entrée donne tel résultat, alors qu’on attendait tel autre. Ensuite, réduire cet exemple : retirer tout ce qui n’est pas nécessaire pour que l’erreur apparaisse. Une liste de 500 ventes qui donne un total faux devient une liste de deux ventes qui donne déjà un total faux. Un petit exemple se raisonne à la main, et il devient ensuite un cas de test.

Puis formuler une hypothèse précise : « je pense que la remise est appliquée deux fois ». Et la vérifier par une expérience : afficher la valeur intermédiaire avec print, ou écrire une assertion à l’endroit suspect. Si l’hypothèse est fausse, on l’abandonne et on en formule une autre ; si elle est vraie, on corrige, puis on relance le test pour confirmer.

Quand l’espace de recherche est grand, la dichotomie, vue dans le cours d’algorithmes, est l’outil le plus puissant. Si le programme fonctionnait le lundi et ne fonctionne plus le vendredi, après vingt modifications, on teste la version du milieu : si elle fonctionne, l’erreur est dans la seconde moitié, sinon dans la première. Cinq essais suffisent pour trouver la modification fautive parmi trente-deux. L’outil git bisect, présenté dans le cours Git de Nunya, automatise exactement cette recherche dans l’historique.

La même idée s’applique aux données : si un fichier de 1 000 lignes fait planter un programme, on essaie la première moitié, puis le quart, jusqu’à isoler la ligne coupable.

Deux habitudes complètent la méthode. Expliquer le problème à voix haute, même à un objet posé sur la table : formuler chaque étape révèle souvent l’hypothèse oubliée. Et ne changer qu’une chose à la fois, pour savoir laquelle a eu un effet.

Enfin, une fois le bug corrigé, on écrit le test qui l’aurait détecté. Le même bug ne reviendra pas sans qu’un test le signale : c’est un test de non-régression.

## Exemple guidé 1

```python
def total(ventes):
    somme = 0
    for quantite, prix in ventes:
        somme = quantite * prix
    return somme

print(total([(2, 600), (1, 1200)]))
print(total([(2, 600)]))
print(total([(1, 1200)]))
```

Affichage attendu :

    1200
    1200
    1200

Trace :

- Le grand exemple donne 1200 au lieu de 2400.
- Avec une seule vente, le résultat est juste.
- Hypothèse confirmée : seule la dernière vente compte ; = devrait être +=.

## Exemple guidé 2

```python
versions = [True, True, True, True, False, False, False, False]
gauche, droite = 0, len(versions) - 1
essais = 0
while gauche < droite:
    milieu = (gauche + droite) // 2
    essais += 1
    if versions[milieu]:
        gauche = milieu + 1
    else:
        droite = milieu
print("Première version cassée :", gauche, "en", essais, "essais")
```

Affichage attendu :

    Première version cassée : 4 en 3 essais

Trace :

- True signifie que la version fonctionne.
- Chaque essai élimine la moitié des versions.
- Trois essais suffisent pour huit versions.
