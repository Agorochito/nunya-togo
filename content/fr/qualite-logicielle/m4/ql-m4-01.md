## Explication pas à pas

Jusqu’ici, tu écrivais d’abord le code, puis les tests. Le développement piloté par les tests, en anglais Test-Driven Development ou TDD, inverse l’ordre. Il avance par cycles très courts de trois étapes, que l’on nomme par la couleur affichée par les outils de test.

Rouge : on écrit un test pour un petit comportement qui n’existe pas encore, et on vérifie qu’il échoue. Cette vérification compte : un test qui passe avant même que le code existe ne teste rien.

Vert : on écrit le code le plus simple possible pour faire passer ce test, sans chercher l’élégance. Si le test attend "pair" pour 4, une première version peut même être naïve ; le test suivant forcera le vrai calcul.

Remanier : maintenant que les tests passent, on améliore le code, de meilleurs noms, moins de répétition, en relançant les tests à chaque modification. Puis on recommence avec un nouveau test rouge.

Cette méthode a plusieurs effets. Elle oblige à préciser le comportement attendu avant de coder, ce qui révèle les questions oubliées : que faire d’un numéro avec des espaces, d’un nombre négatif, d’un texte vide ? Elle garantit que chaque ligne de code est couverte par au moins un test. Elle produit du code facile à tester, puisque le test existait avant lui. Et elle donne un rythme rassurant : on n’est jamais loin d’un état où tout fonctionne.

Prenons un exemple : normaliser un numéro de téléphone togolais à huit chiffres, saisi avec ou sans espaces, au format "+228 90 12 34 56". Premier test : "90123456" doit donner "+228 90 12 34 56". On l’écrit, il échoue, on code le découpage par paires, il passe. Deuxième test : "90 12 34 56" avec des espaces. Il échoue ; on retire les espaces avant de découper. Troisième test : "9012" doit lever ValueError. On ajoute la vérification de longueur. Quatrième test : "90a23456" doit être refusé. On ajoute isdigit. Chaque comportement est né d’un test, et la liste des tests forme une spécification complète.

Le TDD n’est pas une religion. Pour explorer une idée ou un prototype jetable, on code souvent directement. Mais pour une règle métier précise, un calcul de prix, une validation, un format, écrire le test d’abord est une façon fiable d’avancer sans régression. Les exercices de cette leçon te font pratiquer le cycle, avec les mutants pour vérifier que tes tests ont du mordant.

## Exemple guidé 1

```python
def classer(n):
    return "pair" if n % 2 == 0 else "impair"


def test_classer():
    assert classer(4) == "pair"
    assert classer(7) == "impair"
    assert classer(0) == "pair"
    assert classer(-3) == "impair"


test_classer()
print("vert")
```

Affichage attendu :

    vert

Trace :

- Le test a été écrit avant la fonction.
- La fonction la plus simple le fait passer.
- -3 % 2 vaut 1 en Python : le cas négatif fonctionne.

## Exemple guidé 2

```python
def normaliser_tel(texte):
    chiffres = texte.replace(" ", "")
    if len(chiffres) != 8 or not chiffres.isdigit():
        raise ValueError("numéro invalide")
    return "+228 " + " ".join(chiffres[i:i + 2] for i in range(0, 8, 2))

print(normaliser_tel("90 12 34 56"))
try:
    normaliser_tel("9012")
except ValueError as e:
    print(e)
```

Affichage attendu :

    +228 90 12 34 56
    numéro invalide

Trace :

- Les espaces sont retirés avant le découpage.
- Les chiffres sont regroupés par paires.
- Un numéro trop court est refusé.

## Vérifier et expliquer

Fais un cycle TDD complet sur une petite fonction de ton choix et note ce que chaque test t’a obligé à ajouter.
