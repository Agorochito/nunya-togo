## Explication pas à pas

Un programme est écrit une fois, mais il est relu des dizaines de fois : par toi la semaine suivante, par une collègue qui doit le modifier, par la personne qui cherche un bug. Le premier critère de qualité, après l’exactitude, est donc la lisibilité. Deux outils simples y contribuent plus que tout : les noms et la taille des fonctions.

Un bon nom dit ce que contient une variable ou ce que fait une fonction. t, x et l obligent le lecteur à deviner ; total, ligne et lignes l’informent. Une fonction se nomme par un verbe ou par ce qu’elle renvoie : calculer_total, frais_livraison, est_valide. Pour un booléen, un préfixe comme est_ ou a_ rend les conditions lisibles comme une phrase : if est_valide(code). Les abréviations obscures économisent quelques lettres et coûtent des minutes de compréhension. En Python, le guide de style officiel, la PEP 8, recommande les minuscules séparées par des tirets bas pour les variables et les fonctions, et les majuscules pour les constantes.

Une bonne fonction fait une seule chose. Quand une fonction calcule un sous-total, puis des frais, puis formate un ticket, puis l’affiche, elle est difficile à lire, à tester et à réutiliser. On l’extrait en petites fonctions : chacune a un nom qui résume son rôle, et la fonction principale se lit comme une recette : calculer le sous-total, ajouter les frais. Un signe qui ne trompe pas : si tu as besoin d’un commentaire pour expliquer ce que fait un bloc, ce bloc mérite souvent de devenir une fonction dont le nom remplace le commentaire.

Ces petites fonctions se testent séparément. Il est bien plus facile de vérifier frais_livraison sur quatre montants que de construire des factures complètes pour chaque cas. C’est l’une des raisons pour lesquelles un code bien découpé contient moins de bugs.

Ce travail de réorganisation, sans changer le comportement du programme, s’appelle le refactoring, ou remaniement. Sa règle d’or : le programme doit faire exactement la même chose avant et après. On s’appuie donc sur des tests qui passent avant le remaniement et qui doivent toujours passer après. On avance par petits pas, en relançant les tests à chaque étape : renommer, relancer ; extraire une fonction, relancer.

Ne cherche pas la perfection : un nom peut toujours être amélioré plus tard. Mais chaque fois que tu relis ton code et que tu hésites sur le sens d’une ligne, c’est le signal qu’un meilleur nom ou une fonction de plus aideraient le prochain lecteur.

## Exemple guidé 1

```python
def sous_total(lignes):
    return sum(quantite * prix for _, quantite, prix in lignes)


def frais_livraison(montant):
    return 0 if montant >= 20000 else 1500


def total_facture(lignes):
    montant = sous_total(lignes)
    return montant + frais_livraison(montant)

lignes = [("riz", 2, 6000), ("huile", 1, 3500)]
print(sous_total(lignes), frais_livraison(15500), total_facture(lignes))
```

Affichage attendu :

    15500 1500 17000

Trace :

- sous_total additionne quantité × prix.
- frais_livraison applique la règle des 20 000 FCFA.
- total_facture se lit comme une recette.

## Exemple guidé 2

```python
def f(a, b):
    return a - a * b // 100


def prix_remise(prix, pourcentage):
    return prix - prix * pourcentage // 100


print(f(5000, 10), prix_remise(5000, 10))
```

Affichage attendu :

    4500 4500

Trace :

- Les deux fonctions font exactement la même chose.
- Seule la seconde se comprend sans lire son corps.
- Le renommage ne change pas le résultat.
