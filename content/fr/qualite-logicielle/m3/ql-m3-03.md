## Explication pas à pas

Un nom clair dit ce que fait une fonction ; une docstring dit comment l’utiliser. C’est une chaîne entre triples guillemets placée juste sous la ligne def. Python la conserve : help(fonction) l’affiche, et les éditeurs la montrent quand on survole un appel. La PEP 257 décrit les conventions : une première ligne courte qui résume le rôle, puis, si besoin, une ligne vide et des précisions sur les paramètres, le résultat et les erreurs possibles.

Une docstring utile répond aux questions de celui qui appelle la fonction : que dois-je fournir, que vais-je recevoir, que se passe-t-il si l’entrée est invalide ? Elle ne raconte pas le fonctionnement interne, qui peut changer.

Le module doctest ajoute une idée puissante : écrire dans la docstring des exemples sous la forme d’une session Python. Une ligne qui commence par >>> contient un appel, et la ligne suivante le résultat attendu. doctest exécute ces exemples et vérifie que le résultat affiché correspond. La documentation devient un test : si quelqu’un modifie la fonction et oublie la docstring, les exemples échouent et le signalent. Sur un ordinateur, on lance python -m doctest fichier.py ; dans les exercices, une fonction de vérification fournie fait ce travail.

Les annotations de types complètent la documentation : def duree(texte: str) -> int annonce qu’on attend un texte et qu’on renvoie un entier. Pour une liste de nombres décimaux, on écrit list[float] ; pour un dictionnaire, dict[str, int]. Python ne vérifie pas ces annotations à l’exécution : elles servent au lecteur, aux éditeurs, qui signalent les erreurs, et à des outils comme mypy, qui analysent tout un projet sans l’exécuter.

Faut-il tout documenter ? Non. Une petite fonction privée au nom évident peut s’en passer. En revanche, toute fonction utilisée ailleurs, et surtout celles qui ont des cas particuliers, mérite une docstring et des exemples. Un bon réflexe : si tu dois expliquer une fonction à voix haute à un collègue, écris plutôt cette explication dans sa docstring.

Le danger d’une documentation est de devenir fausse : la fonction change, la docstring reste. Une docstring fausse est pire que pas de docstring, car on la croit. Les doctests limitent ce risque pour les exemples ; pour le reste, on relit la docstring à chaque modification de la fonction, comme on relit les tests.

## Exemple guidé 1

```python
def duree(texte: str) -> int:
    """Convertit une durée "HhMM" en minutes.

    >>> duree("1h30")
    90
    >>> duree("0h05")
    5
    """
    heures, minutes = texte.split("h")
    return int(heures) * 60 + int(minutes)

print(duree("2h15"))
print(duree.__doc__.splitlines()[0])
print(duree.__annotations__)
```

Affichage attendu :

    135
    Convertit une durée "HhMM" en minutes.
    {'texte': <class 'str'>, 'return': <class 'int'>}

Trace :

- La fonction convertit 2 h 15 en 135 minutes.
- Python garde la docstring dans __doc__.
- Les annotations sont conservées dans __annotations__.

## Exemple guidé 2

```python
import doctest


def double(n):
    """
    >>> double(4)
    8
    >>> double(-1)
    -3
    """
    return n * 2


runner = doctest.DocTestRunner()
for test in doctest.DocTestFinder().find(double, "double", module=False, globs={"double": double}):
    runner.run(test, out=lambda texte: None)
print(runner.tries, "exemples,", runner.failures, "échec")
```

Affichage attendu :

    2 exemples, 1 échec

Trace :

- doctest exécute les deux exemples de la docstring.
- double(-1) donne -2, pas -3 : l’exemple est faux.
- La documentation fausse est détectée.
